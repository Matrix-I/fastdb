# P2-04 data and schema search

1. Expand PostgreSQL definition discovery to native catalog families with
   available definitions. Preserve object identity and bounded previews.
2. Add data search on a selected connection and table scope. Use read-only
   requests with bound terms, bounded results, explicit progress and cancel.
   Navigate through verified row identity and explain limitations for rows
   that have no safe locator.
3. Validate search, permissions, cancellation and navigation on isolated
   engines. Inspect real query plans for scoped catalog and table searches.
   Record supported providers, object families and manual desktop acceptance.

Keep the plan uncommitted because the user has not requested a commit.

## PostgreSQL catalog expansion evidence

PostgreSQL 16, disposable local fixture with 4,000 views, 4,000 routines,
400 indexed tables and 400 user rules. One quarter of each family was in the
selected schema. The candidate fence kept the native deparsers downstream of
the schema restriction. On the same fixture shape:

| Search | Before fence | After fence |
| --- | ---: | ---: |
| Matching, 51 rows | 34.926 ms, 37,593 hits and 1 read | 16.146 ms, 8,130 hits |
| No match, 0 rows | 26.656 ms, 24,764 hits | 13.912 ms, 6,527 hits |

The matching sort used a 28 KiB top-N heap with no spill. Plans used system
catalog scans and indexed catalog joins. Only catalog metadata and native
definitions were read. These are local measurements, not deployment targets.

## Table-search workflow to implement

Use the navigator connection and exact schema, then an explicit table selection.
Match a literal case-insensitive substring against supported scalar columns
according to each engine's collation. Skip binary columns and SQL NULL. Return
bounded snippets, table/column identity and a total cap of 50 displayed matches.
Report which tables have completed and stop the active search on Cancel.

Reuse the connection and metadata identity guard when opening results. A
complete primary key can drive exact-row navigation through an engine-bound
lookup. A keyless hit can still open its captured match; report that the current
row cannot be reopened safely. Keep source types, object kinds and provider
coverage explicit in the UI and guide. Cover duplicate table names, composite
keys, stale rows, missing privileges, literal wildcard input and lock-based
cancellation on disposable engines.

## PostgreSQL single-table search evidence

The single-table path uses an ephemeral heap locator made of relation OID,
relfilenode, tuple position and row version. It can reopen the same visible
row without a primary key and rejects updates and heap rewrites. The locator
stays in the search dialog and is never saved. The preview contains the
matching column and up to 31 other supported scalar columns.

A PostgreSQL 16 fixture had 100,000 rows and two searchable columns. The
literal infix match used a sequential scan with an in-memory two-value scan
per row and no sort. It stopped after reading 51,000 rows and returned 51
matches in 43.023 ms (276 buffer hits). No match scanned 100,000 rows in
85.990 ms (541 hits). PostgreSQL estimated one row per lateral lookup, so
the no-match cardinality estimate was high. The inner loop reads only two
in-memory values per table row and does not repeat table or index I/O.
Exact reopen used a TID scan and took 0.007 ms (1 hit). A scoped role lacked table SELECT before the grant and saw only its
one permitted row once the grant and row-level security policy applied.


## PostgreSQL table scope

The navigator picker uses exact schema names and up to 32 selected tables
from loaded metadata. The existing table footer remains a single-table
shortcut. Scan one table at a time in name order, preserve completed
matches and report errors per table. Stop after the shared 50-hit limit or
cancellation. The same bound one-table SQL and row lookup are reused;
scope selection does not introduce another SQL query.
