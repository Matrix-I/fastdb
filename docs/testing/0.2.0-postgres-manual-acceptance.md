# v0.2.0 PostgreSQL manual acceptance

Release scope confirmed on 2026-11-05: **PostgreSQL is the required provider**.
MariaDB, Oracle, SQL Server and Db2 are disabled with **Feature is coming**.
MySQL and SQLite remain available but are not required by this acceptance run.
Do not mark any unchecked or blocked case as passed. This runbook is a protocol,
not a record that the GUI passed. No Computer Use is required.

## Recording and preparation

Record build commit/version, macOS version, architecture, normal/HiDPI scaling,
PostgreSQL version and tester/date. Run the entire checklist against the same
candidate binary; repeat affected cases after a fix and finish with the final
candidate's startup/restart/Quit smoke. Allow about 2–3 hours, plus transport and
failure-injection setup. Record each case as `PASS`, `FAIL`, or `BLOCKED` with the
actual result and screenshot/log path. Never include passwords or secret fields.

1. Prepare two **new disposable databases**, `fastdb_accept_a` and
   `fastdb_accept_b`, using an independent PostgreSQL client. Never use production.
   Set up a matching psql service for each database (`accept_a`, `accept_b`), with
   authentication in your normal secure client configuration. Commands below use
   those service names and do not contain credentials.
2. Run [fixture SQL](0.2.0-postgres-fixture.sql) once per database:
   ```bash
   psql 'service=accept_a' -X -v ON_ERROR_STOP=1 -f docs/testing/0.2.0-postgres-fixture.sql
   psql 'service=accept_b' -X -v ON_ERROR_STOP=1 -f docs/testing/0.2.0-postgres-fixture.sql
   ```
   Expected baseline counts: `1000, 3, 1, 2, 0, 0, 0`. The fixture does not drop
   existing data. For a fresh run on these same disposable databases, use the
   cleanup/reset steps below before loading the fixture again.
3. Use a separate FastDB profile. For the functional pass, launch the candidate
   executable with `FASTDB_CONFIG_DIR=/tmp/fastdb-020-manual` and leave
   `FASTDB_LOCAL_CREDENTIALS` unset so Keychain is exercised. Use the same profile
   and candidate for restarts. Keep an independent psql session for read-back.
4. Name saved profiles `Accept A` and `Accept B`, pointing to their respective
   databases. Use different navigator colors and one common group. Keep them
   connected concurrently. All main steps below use A unless B is specified.
5. The fixture names are reserved for this run. Use IDs above 1000 for scratch
   inserts. Do not rerun setup in the middle of a test to hide unexpected changes.

## Reset and repeat from the beginning

Close or roll back active test transactions in FastDB and external clients first.
Run [cleanup SQL](0.2.0-postgres-cleanup.sql) against **each disposable database**,
then reload the fixture. Cleanup removes `release_check` and `release_other`, all
their data and dependent objects, including scratch objects created inside them.
Do not keep unrelated objects in or dependent on these reserved schemas.
Database names, roles and FastDB saved profiles/scripts/preferences are retained.
Scratch objects created outside these schemas require separate cleanup.

From the repository root:

```bash
psql 'service=accept_a' -X -v ON_ERROR_STOP=1 -f docs/testing/0.2.0-postgres-cleanup.sql
psql 'service=accept_a' -X -v ON_ERROR_STOP=1 -f docs/testing/0.2.0-postgres-fixture.sql
psql 'service=accept_b' -X -v ON_ERROR_STOP=1 -f docs/testing/0.2.0-postgres-cleanup.sql
psql 'service=accept_b' -X -v ON_ERROR_STOP=1 -f docs/testing/0.2.0-postgres-fixture.sql
```

Stop if any command fails. The cleanup is safe to repeat when either schema is
already absent. Both drops run in one transaction with a 3-second lock timeout
and a 15-second per-statement timeout; an error must not be ignored. After reset,
expect fixture counts `1000, 3, 1, 2, 0, 0, 0`, reconnect/refresh FastDB, close stale
result/column tabs and start at C01 with a fresh copy of the result checklist.
Use a new isolated FastDB profile if connection/preference tests also need a
first-launch state; database cleanup does not reset application state.
